# Daily Health API

The daily health API saves daily health log entries from the barcode scanner service into the EHR study's Daily Health Log dataset. It is a plain HTTP JSON endpoint, so any client that can send HTTP requests can call it.

## Endpoint

```
POST https://<server>/<ehr-folder-path>/nbri_ehr-saveDailyHealth.api
Content-Type: application/json
```

`<ehr-folder-path>` is the path of the EHR study folder, for example `NBRI/EHR`.

## Authentication with an API key

1. A site administrator turns on API keys under Admin Console > Site Settings (the "Let users create API keys" setting).
2. Sign in as the account the scanner service will use, open the user menu, choose **API Keys**, and generate a key. Store it as a secret; it acts as that user.
3. Send the key in an `apikey` header on every request.

The account needs permission to insert Completed records in the EHR study folder, for example the **EHR Data Entry** role together with **EHR Full Submitter**. Every saved row and task records this account as its creator; the technician comes from each entry.

### CSRF token

LabKey requires a CSRF token on every POST, including API key requests. Get one by calling `login-whoami.api` with the key, keep the cookie it sets, and send the token back in an `X-LABKEY-CSRF` header along with that cookie:

```bash
APIKEY='apikey|0123456789abcdef...'
SERVER='https://labkey.example.org'

# 1. Fetch the CSRF token, saving the cookie it is tied to
curl -s -H "apikey: $APIKEY" -c cookies.txt "$SERVER/login-whoami.api"
# => { "id": 1004, "email": "scanner@example.org", "CSRF": "4f1c...", "success": true, ... }

CSRF='4f1c...'   # the "CSRF" value from the response above

# 2. Send entries with the key, the token and the cookie
curl -s -X POST \
  -H "apikey: $APIKEY" \
  -H "X-LABKEY-CSRF: $CSRF" \
  -b cookies.txt \
  -H "Content-Type: application/json" \
  --data @entries.json \
  "$SERVER/NBRI/EHR/nbri_ehr-saveDailyHealth.api"
```

The token and cookie can be reused for later requests from the same client. If a POST comes back with HTTP 401 and "This request has an invalid security context", fetch a new token.

Clients that can't send custom headers can pass the key with HTTP Basic authentication instead, using `apikey` as the username and the key as the password. The CSRF steps are the same.

## Request

The body is a JSON object with an `entries` array. Each entry is one log entry: one animal observed once, with one or more codes.

| Field | Required | Description |
|---|---|---|
| `logEntryId` | yes | UUID that identifies the entry, generated by the scanner (UUIDv7 recommended). It becomes the entry's EHR task id. Case doesn't matter. |
| `animalId` | yes | Id of a living animal. |
| `observationDateTime` | yes | ISO 8601 date-time. With an offset (`2026-11-09T07:30:00-08:00`) it is converted to server time; without one (`2026-11-09T07:30:00`) it is taken as server time. |
| `technician` | yes | Email or display name of an active LabKey user. |
| `locationArea` | yes | Building the animal was scanned in. |
| `locationEnclosure` | yes | Room name within that building. |
| `locationCage` | no | Cage within that room. Omit it to check the room only. |
| `codes` | yes | At least one `{ "code": ..., "sortOrder": ... }`. `code` must be an enabled daily health code; `sortOrder` is a number, unique within the entry, giving the order the codes were recorded in. |

The location must match the animal's housing at the observation time: the room is looked up as `<locationArea>-<locationEnclosure>` and the cage as `<locationArea>-<locationEnclosure>-<locationCage>`. The location is only checked; it isn't stored with the entry.

Example `entries.json` with one good entry and one that will be rejected:

```json
{
  "entries": [
    {
      "logEntryId": "019a6a2e-7c3f-7b21-9d4e-5f1a2b3c4d5e",
      "animalId": "12345",
      "observationDateTime": "2026-11-09T07:30:00-08:00",
      "technician": "tech@example.org",
      "locationArea": "B1",
      "locationEnclosure": "R1",
      "locationCage": "C1",
      "codes": [
        { "code": "HEVYMEN", "sortOrder": 1 },
        { "code": "NRMLMEN", "sortOrder": 2 },
        { "code": "POORAPP", "sortOrder": 3 }
      ]
    },
    {
      "logEntryId": "019a6a2e-7c40-7d55-8a11-0b2c3d4e5f60",
      "animalId": "12345",
      "observationDateTime": "2026-11-09T07:31:00-08:00",
      "technician": "tech@example.org",
      "locationArea": "B1",
      "locationEnclosure": "R1",
      "locationCage": "C2",
      "codes": [
        { "code": "RAB", "sortOrder": 1 }
      ]
    }
  ]
}
```

## What a save does

- Each entry saves on its own, with its own EHR task (task id = `logEntryId`), so a bad entry doesn't stop the others in the batch. Within an entry it is all or nothing: a rejected entry leaves no rows and no task behind.
- Each code becomes one Daily Health Log row with the entry's animal, date, technician and `logEntryId`, in the Completed QC state.
- `HEVYMEN`/`NRMLMEN` create a Menses clinical observation (heavy wins if both are sent), `POORAPP` an Appetite observation and `LIQDSTL` a Stool observation, once per entry.
- Sending an entry whose `logEntryId` is already on file saves nothing and reports `exists`, so a scanner can safely resend a batch after a timeout.

## Response

HTTP 200 means the batch was processed; check each entry's result. `success` is `true` only if no entry has status `error`.

```json
{
  "success": false,
  "results": [
    {
      "logEntryId": "019a6a2e-7c3f-7b21-9d4e-5f1a2b3c4d5e",
      "status": "created",
      "errors": []
    },
    {
      "logEntryId": "019a6a2e-7c40-7d55-8a11-0b2c3d4e5f60",
      "status": "error",
      "errors": [ "12345 was not housed in B1-R1-C2 on 2026-11-09" ]
    }
  ]
}
```

| `status` | Meaning |
|---|---|
| `created` | The entry and its task were saved. |
| `exists` | An entry with this `logEntryId` is already on file; nothing was saved. |
| `error` | Nothing was saved for this entry; `errors` says why. |

Entry errors you can expect:

| Error | Cause |
|---|---|
| `logEntryId must be a UUID` | Missing or malformed `logEntryId`. |
| `animalId is required` / `technician is required` / `observationDateTime is required` | Missing field. |
| `observationDateTime must be an ISO 8601 date-time: ...` | The date-time didn't parse. |
| `locationArea and locationEnclosure are required` | Missing location. |
| `codes must list at least one code` / `codes[N] needs a code and a numeric sortOrder` | Missing or malformed codes. |
| `<technician> is not an active LabKey user` | No active user with that email or display name. |
| `<animal> is not a living animal` | The animal isn't alive. |
| `<animal> was not housed in <location> on <date>` | The location doesn't match the animal's housing at that time. |
| `Unknown daily health code: <code>` / `Daily health code <code> is retired` | The code isn't in the code list, or is disabled. |
| `Another row of this log entry has sort order N` | Two codes in the entry share a sort order. |

Request-level failures:

| HTTP status | Cause |
|---|---|
| 400 | The body isn't a JSON object with an `entries` array (`"exception": "Expected a JSON body with an 'entries' array"`). |
| 401 | Missing or invalid API key, the account lacks permission, or the CSRF token or cookie is missing or stale. |
